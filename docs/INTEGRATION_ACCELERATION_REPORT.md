## 4. الوحدات المكتملة على فرع التطوير

المكتمل يعني واجهة تستدعي الـ API الموجود، مع اختبارات PGlite للخدمة. لا يعني جاهزية إنتاج.

- المخزون: الأصناف والمستودعات والحركات. الدفتر إلحاق فقط.
- المشتريات حتى الدفع: طلب، أمر، استلام، فاتورة مورد، مرتجع، إشعار دائن، دفعة، مطابقة، تسوية دفتر.
- المالية: فواتير البيع والتحصيل ودفتر الأستاذ والفترات وميزان المراجعة.
- المبيعات الموجودة: عرض سعر ثم فاتورة ثم تحصيل. لا أمر بيع بينهما.
- الذكاء: قواعد حتمية وموافقة بشرية.
- المنظمة والهوية: الـ API كان موجودًا، والشاشات أُضيفت في هذه الموجة.

لوحة الصفحة الرئيسية (`/` وأقسام مثل الفروع والمطبخ) ما زالت تعرض أرقامًا ثابتة داخل المكوّنات. مسارات `/erp` لا تستخدم تلك الأرقام. لم تُحذف اللوحة، ولم تُعلَّم كمعاينة في هذه الجلسة.

## 5. العوائق الحرجة

- migrations `0009` إلى `0016` مكتوبة ومُثبتة على PGlite، وغير مطبّقة على PostgreSQL حقيقي. لا Docker ولا `psql` ولا `pg_ctl` على الجهاز. لم تُثبَّت قاعدة، ولم يُشغَّل `staging-validate.mjs` ولا `migrate.mjs`. الأداة نفسها ترفض العمل بلا `--expect-host` و`--i-understand-this-is-staging`، ولا تطبّق ترحيلًا، وتعمل داخل معاملة تُلغى.
- PGlite يسلسل المعاملات، فاختبارات التزامن تثبت الناتج لا قفل `for update` الحقيقي.
- إصدار فاتورة بيع ينقص المخزون ولا يرحّل تكلفة البضاعة. هذا موثّق في `docs/OPEN_ACCOUNTING_DECISIONS.md` ولم يُبنَ له قيد.
- محدد المعدل عملية واحدة في الذاكرة. لا يحمي عدة نسخ من الخادم.
- مستخدم بعضويتين لا يرى صلاحيات، لأن المتصفح لا يرسل المؤسسة المختارة.
- الشاشات الجديدة لم تُفتح في متصفح. البناء نجح، والجلسة لم تُنشأ على بيانات حقيقية.
- الالتزامات غير مدفوعة، وCI على GitHub لم يُشغَّل لأن الفرع لم يُدفع.
