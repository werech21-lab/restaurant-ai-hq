## 1. مبادئ تحكم كل المجالات

1. كل جدول: `tenant_id, created_at, updated_at, created_by` و`version` عند إمكان التعديل المتزامن.
2. المبالغ أعداد صحيحة بوحدات صغرى (`bigint`/`BigInt`)، والعملة KWD فقط حتى قرار آخر. لا floats، والتقريب مرة واحدة لكل مستند.
3. الدفاتر (قيود، حركات مخزون، مدفوعات) **append-only**؛ التصحيح بقيد أو حركة عكسية.
4. لا حذف مادي لسجل مالي. كل كتابة مؤثرة تكتب صف تدقيق (من، ماذا، متى، قبل، بعد).
5. التعامل بين الوحدات عبر واجهتها العامة (`index.ts`) أو حدث مؤطَّر (`docs/EVENT_DESIGN.md`)، وبدوال `...Within` داخل معاملة المُستدعي.
6. الأحداث بعد الـ commit فقط، والمعالجات متكافئة.
7. أي جدول جديد يحتاج: RLS قراءة فقط للمتصفح، صلاحيات `grant` صريحة، اختبار PGlite يثبت العزل، وحالة في `staging-validate`.

## 2. أين يعيش كل مجال (انحراف يحتاج قراراً)

`erp-core.mdc` يحدد خمس وحدات فقط: `finance, crm, inventory, hr, ai`. لذلك:

| المجال | المقترح | السبب |
| --- | --- | --- |
| المحاسبة والقيود المزدوجة | داخل `finance` (مجلد `ledger/`) | حسابات وقيود جزء من المالية |
| المخزون والتقييم | `inventory` (موجود) | |
| المشتريات والموردون | **وحدة جديدة `procurement`** | لا مكان طبيعي لها بين الخمس. تحتاج موافقتك على إضافتها لقاعدة `erp-core.mdc` |
| المبيعات والفواتير | `finance` + `crm` (موجودان) | |
| العقود والملاحق | **وحدة جديدة `contracts`** أو داخل `crm` للعقود مع العملاء فقط | قرار: هل تشمل عقود الموردين؟ |
| العلامات التجارية والفروع | بنية مشتركة `src/lib/org` (مثل `src/lib/iam`) | تقاطع كل الوحدات |
| التدقيق والموافقات | بنية مشتركة `src/lib/approvals` فوق `audit_log` الموجود | تقاطع كل الوحدات |

## 3. المحاسبة والقيود المزدوجة

قرارك السابق: «فواتير ومدفوعات فقط، بلا دفتر أستاذ». هذا التصميم **لا يتعارض** معه: يُبنى كطبقة تالية، وتبقى الفواتير والمدفوعات مصدر الحقيقة، والقيود تُشتق منها.

**الجداول المقترحة**

- `accounts` (`id, tenant_id, code, name, type [asset|liability|equity|revenue|expense], parent_id, is_postable, is_active`) فريد `(tenant_id, code)`.
- `fiscal_periods` (`tenant_id, starts_on, ends_on, status [open|closed]`) بلا تداخل (exclusion constraint).
- `journal_entries` (`id, tenant_id, period_id, entry_date, source_type, source_id, memo, reverses_id, posted_at, posted_by`). **append-only**.
- `journal_lines` (`entry_id, line_no, account_id, debit_minor bigint, credit_minor bigint`) مع `check (debit_minor >= 0 and credit_minor >= 0 and (debit_minor = 0) <> (credit_minor = 0))`.

**الثوابت (يفرضها قاعدة البيانات)**

1. مجموع المدين = مجموع الدائن لكل قيد (`constraint trigger ... deferrable initially deferred`).
2. لا قيد في فترة مغلقة. لا تعديل ولا حذف لقيد. العكس بقيد `reverses_id`.
3. العملة KWD، والمبالغ بالفلس.
4. مفتاح فريد `(tenant_id, source_type, source_id)` يمنع ترحيل المستند مرتين.

**الترحيل التلقائي** يستهلك أحداث `finance.invoice.issued` و`finance.payment.recorded` و`finance.invoice.voided` ويكتب القيد عبر دالة `postJournalWithin` داخل معاملة. جدول `posting_rules` يربط نوع المستند بالحسابات.

**قرارات تحتاج جواباً منك (لن أخمّنها):** (أ) هل يُبنى دفتر الأستاذ الآن؟ (ب) شجرة الحسابات الافتراضية. (ج) حسابات ضريبة المبيعات (القاعدة الحالية: ضريبة لكل بند بنقاط أساس دون تحديد نسبة أو حساب). (د) تعدد العملات (اليوم KWD فقط). (هـ) سياسة إغلاق الفترات ومن يملك صلاحيتها.

## 4. المخزون وحركاته وتقييمه

الموجود يكفي للكميات. الفجوة هي **القيمة**:

- القاعدة: `التقييم = الرصيد × unit_cost_minor` ولا طريقة تكلفة أخرى دون سؤالك. هي تقييم **بآخر تكلفة معرّفة للصنف** لا تاريخ تكلفة لكل حركة.
- لربط المخزون بالمحاسبة (قيد استلام وقيد صرف) نحتاج **تكلفة الحركة** وقت وقوعها، وهذا يتطلب تحديد الطريقة.

**قرار مطلوب:** هل تُسجَّل تكلفة الحركة بآخر `unit_cost_minor` (الأبسط، متسق مع القاعدة)، أم بمتوسط مرجّح أو FIFO؟ حتى تقرر: لا عمود تكلفة على الحركات ولا قيود مخزون.

**ما يمكن بناؤه دون قرار:** جرد دوري `stocktakes` (عدّ فعلي ← حركات تسوية عبر `stock_movements` فقط، بلا كتابة مباشرة في الأرصدة)، وحدود إعادة الطلب (موجودة).

## 5. المشتريات والموردون

**الجداول:** `suppliers` (حالة `active|blocked`، لا حذف، الحظر بدلاً منه كما في العملاء)، `purchase_orders` + `purchase_order_lines`، `goods_receipts` + بنودها، `supplier_invoices` (ذمم دائنة) + `supplier_payments`.

**التدفق المقترح لأمر الشراء:** `draft → pending_approval → approved → partially_received → received | cancelled`. قاعدة: الاستلام يُنشئ حركات `IN` عبر دالة `receiveGoodsWithin` من `@/modules/inventory` فقط، والمشتريات لا تقرأ جداول المخزون. الإيقاف على صنف أو مستودع غير نشط مفروض من المخزون.

**الموافقة:** أمر شراء فوق حد قابل للضبط في `procurement_settings` (مثل `finance_settings.approval_threshold_minor`، لا قيمة مكتوبة في الشيفرة).

**قرارات:** حالات أمر الشراء النهائية، حد الموافقة، المطابقة الثلاثية (أمر/استلام/فاتورة) هل هي إلزامية، وسياسة تجاوز الكمية المستلمة.

## 6. المبيعات والفواتير

موجودة ومكتملة للمسار: عرض سعر ← فاتورة ← دفعة، مع حد ائتمان وموافقة. ما ينقص:

- **إشعار دائن** (`credit_notes`) لتصحيح فاتورة صدرت: القاعدة «لا حذف، عكس أو إشعار دائن» تتوقعه، لكن قرارك الحالي «فواتير ومدفوعات فقط». **قرار:** هل يُضاف؟ وإن أُضيف فهو انتقال حالة جديد يحتاج موافقتك صراحة.
- أوامر بيع قبل الفاتورة: **لا يُضاف** دون طلب (عرض السعر المقبول يؤدي الدور اليوم).

## 7. العقود والملاحق

**الجداول:** `contracts` (`counterparty_type [customer|supplier], counterparty_id, number, status [draft|active|suspended|expired|terminated], starts_on, ends_on, value_minor, auto_renew, current_version`)، `contract_versions` (append-only، كل نسخة تحمل البنود كاملة وهاش المحتوى)، `contract_amendments` (`contract_id, from_version, to_version, reason, effective_on, approval_request_id`).

**الثوابت:**

1. الملحق **لا يعدّل** العقد، بل يُنشئ نسخة جديدة. النسخ السابقة لا تتغير.
2. العقد النشط لا تُعدَّل نسخته الحالية؛ كل تغيير ملحق بموافقة.
3. `ends_on >= starts_on`، ولا عقد نشط بلا طرف مقابل نشط (عميل غير محظور).
4. الانتهاء بلا مجدول: تُحسب الحالة الفعلية بـ `effectiveStatus` كما في عروض الأسعار.

**قرارات:** هل العقد يولّد فواتير دورية (يحتاج مجدولاً غير موجود؟ القاعدة: لا طابور دون طلب)، وقوالب البنود، ومن يوقّع.

## 8. العلامات التجارية والفروع

**الهيكل:** `tenant → brand → branch`. الجداول: `brands (tenant_id, name, status)`, `branches (tenant_id, brand_id, name, code, status, timezone)`.

**البعد التحليلي:** عمود `branch_id` (nullable) على الجداول التشغيلية (فواتير، حركات مخزون، مدفوعات، قيود) لتجميع الأداء حسب الفرع. المؤسسة تبقى حد العزل الأمني، والفرع **بعد تقارير وصلاحية اختيارية**، لا حد عزل.

**نطاق الصلاحية (قرار):** هل يقتصر عضو على فرع أو أكثر؟ إن نعم: جدول `member_branch_scopes` وشرط إضافي في RLS والخدمات. هذا يغيّر كل استعلام قائم ولذلك لا يُبدأ دون موافقة صريحة.

## 9. التدقيق والموافقات

- **التدقيق (موجود):** `audit_log` لكل إنشاء/تعديل/حذف. يُضاف لاحقاً فحص تطابق: كل حدث `iam.*`/مالي له صف تدقيق.
- **الموافقات الموحّدة (مقترح):** `approval_policies (tenant_id, entity_type, condition_json, steps)` و`approval_requests (entity_type, entity_id, status, requested_by, version)` و`approval_decisions (request_id, step, decided_by, decision, reason)` append-only.
  - **فصل المهام:** من أنشأ لا يوافق (يُفرض في الخدمة وبقيد قاعدة بيانات).
  - **تصعيد:** لا تصعيد تلقائي دون مجدول (قرار).
  - الموافقة المالية الحالية (حد `finance_settings`) تبقى كما هي حتى يتقرر ترحيلها لهذا المحرك.

### 12.2 ما بقي تصميماً فقط (لم يُنفَّذ، ويحتاج موافقتك)

**أ. أوامر البيع (عرض سعر ← طلب ← فاتورة ← تحصيل).** اليوم: عرض السعر يتحول إلى فاتورة مباشرة بزر Convert (قاعدة CRM). إدخال "طلب بيع" يغيّر هذا المسار. المقترح: `sales_orders` بحالات `draft ← confirmed ← partially_invoiced ← invoiced | cancelled`، يُنشأ من عرض مقبول، والفاتورة تُنشأ من الطلب (كامل أو جزئي) عبر `createInvoiceWithin`، ولا يخصم المخزون إلا عند إصدار الفاتورة (كما اليوم). **أسئلة:** هل يُحجز المخزون عند تأكيد الطلب؟ هل تُسمح فوترة جزئية؟ هل يبقى زر Convert المباشر؟ الإشعار الدائن (القرار 6) مرتبط بها.

**ب. العقود والملاحق.** المقترح: `contracts` (طرف، نوع: عميل/مورد، `status`)، و`contract_versions` **append-only** (كل ملحق صف جديد بـ `effective_from` و`effective_to` وقيد استبعاد `exclusion constraint` على `daterange` يمنع تداخل نسختين نافذتين)، و`contract_cost_lines` تربط النسخة بمورد أو صنف أو مبلغ دوري. **أسئلة:** هل ربط التكاليف يولّد التزامات أو فواتير تلقائياً (يحتاج مجدولاً، القرار 8)؟ ما الحالات (مسودة ← نافذ ← منتهٍ ← ملغى)؟ هل الملحق يحتاج موافقة؟

**ج. فاتورة المورد والمطابقة الثلاثية** (أمر ← استلام ← فاتورة). *بُنيت فاتورة المورد بقيد مزدوج في القسم 13، أما المطابقة بتسامح السعر/الكمية فلم تُبنَ.* تحتاج: القرار 1 (حساب الدائنين)، القرار 2 (كيف تتحول تكلفة الشراء إلى قيمة مخزون)، وقواعد تسامح السعر والكمية. لم تُبنَ.

**د. الترحيل المحاسبي التلقائي** (فاتورة مبيعات ← قيد، استلام ← قيد). يحتاج شجرة حسابات معتمدة وربط حسابات لكل حدث. لم يُبنَ، وكذلك فترات الافتتاح والإقفال الختامي، وإعادة فتح فترة (الإقفال نهائي حالياً).

**هـ. تكلفة المخزون (القرار 2).** `items.unit_cost_minor` لا يتغير باستلام الشراء. التقييم ما زال `الكمية × التكلفة`.

**و. إرجاع مشتريات للمورد، ومحرك الموافقات الموحّد، والمجدول.**

| القرار | ما فُعل | لماذا |

| موافقة طلب الشراء | أي حامل لـ `procurement.request.approve` يقرر. لا حد مبلغ ولا فصل مهام | لا توجد قاعدة معتمدة. حد أمر الشراء يبقى في `procurement_settings` |
| تحويل الطلب إلى أمر | ينشئ **مسودة** أمر؛ المشتري يختار المورد ويسعّر كل بند، ثم تسري قواعد الإرسال والموافقة المعتادة | الطلب لا يحمل سعراً ولا مورداً |
| حسابات القيد | جدول `procurement_accounting` لكل مؤسسة: مدين المخزون (أصول) بالصافي، مدين ضريبة المدخلات (أصول، فقط إن وُجدت ضريبة) ودائن الموردين (خصوم) بالإجمالي. **لا يُرحَّل شيء قبل ضبطها** (409 `accounts_not_configured`) | لا شجرة حسابات معتمدة (القرار 1) |
| الاستلام والمحاسبة | الاستلام يدخل المخزون فقط ولا يقيّد في الدفتر؛ لا GRNI، ولا يتغير `unit_cost` | طريقة التكلفة قرار مفتوح (القرار 2) |
| سعر فاتورة المورد | يؤخذ سعر وضريبة بند الأمر. سعر مختلف عند المورد لا يُقبل ولا يُخمَّن. الإجمالي المطبوع (اختياري) يجب أن يطابق إلى الفلس | لا تسامح سعري معتمد |
| الكمية المفوترة | ≤ المستلم − المفوتر سابقاً (الملغاة مستثناة)، تُفرض في الخدمة وبـ trigger في قاعدة البيانات | منع الفوترة المزدوجة |
| الإلغاء | قيد عكسي مرحَّل ثم الفاتورة `void`، والكمية تعود قابلة للفوترة. قيد الفاتورة لا يُعكس إلا عبر الإلغاء (خدمة + trigger) | لا تعديل ولا حذف |
| تاريخ الاستحقاق | تاريخ الفاتورة + `payment_terms_days` للمورد | لا قاعدة أخرى |
| العملة | KWD فقط. قيد `CHECK currency = 'KWD'` في كل جدول هو نقطة التخفيف الوحيدة لتعدد العملات | لا أسعار صرف |
| غير مبني وقتها | دفعات الموردين، إشعارات الدائن، مرتجعات المشتريات، المطابقة الثلاثية بتسامح | بُنيت في المرحلة 1.4 (القسم 14) بقرارات مؤقتة |
## 14. إكمال المشتريات مالياً (المرحلة 1.4) — GRNI والمطابقة الثلاثية والدفعات

الترحيلة `0015_p2p_financial_completion.sql` (**لم تُطبَّق على أي قاعدة حقيقية**) تضيف: قيد الاستلام مقابل GRNI، مطابقة فاتورة المورد مع أمر الشراء والمستلم بتسامح، مرتجعات المشتريات، إشعارات دائن الموردين، ودفعات الموردين مع التسوية. التفاصيل والنتائج في `PHASE_1_4_REPORT.md`.

### 14.1 قرارات مؤقتة تحتاج موافقتك (لم تُخمَّن، وُضع أضيق خيار آمن)

| القرار | ما فُعل | لماذا |
| --- | --- | --- |
| أساس القيد | يُختار لكل مؤسسة في `procurement_accounting.accounting_basis`. الافتراضي `invoice_basis` (ما بنته 0014). `receipt_basis` هو الجرد المستمر مع GRNI. لا يتغير الأساس بعد وجود أي مستند عليه، وكذلك الحسابات بعد أول قيد | تغييره يقسم رصيداً واحداً على حسابين |
| قيد الاستلام (receipt_basis) | مدين المخزون ودائن GRNI بسعر أمر الشراء. لا يُغيَّر `unit_cost` للصنف | طريقة التكلفة قرار مفتوح (القرار 2): لم أخترع FIFO ولا متوسطاً |
| قيد الفاتورة (receipt_basis) | مدين GRNI بصافي سعر الأمر، ومدين/دائن فروقات سعر الشراء (PPV) بصافي ما فوتره المورد ناقص صافي الأمر، ومدين ضريبة المدخلات، ودائن الموردين بالإجمالي | يُطفئ GRNI بالضبط ويُظهر الفرق في حسابه |
| قيد الفاتورة (invoice_basis) | مدين المخزون بصافي الفاتورة، ومدين الضريبة، ودائن الموردين | كما في 0014 |
| تسامح السعر | بنقاط أساس من سعر الأمر، على كل بند. الصفر (الافتراضي) لا يسمح بأي فرق. فوق التسامح = 409 `price_variance_exceeded` ولا يُكتب شيء | لا قاعدة معتمدة. لا يوجد مسار موافقة على الفرق فوق التسامح (يحتاج قرارك) |
| فرق الضريبة | ضريبة الفاتورة ناقص الضريبة بمعدلات **الأمر** على الأسعار المفوترة، وتسامحه بالفلس. فرق السعر لا يُحتسب فرق ضريبة | يفصل خطأ المعدل عن خطأ السعر |
| الكمية القابلة للفوترة | المستلم − المرتجع − (المفوتر − المخصوم بإشعارات الدائن). تُفرض في الخدمة وبـ trigger مع قفل بند الأمر | منع الفوترة فوق ما يُحتفظ به |
| المرتجع | بسعر الأمر، من مخزن يملك الكمية، لا يتجاوز المستلم الذي لم يُرجَع. يخفض المخزون بحركة `OUT`. على receipt_basis قيده مدين GRNI ودائن المخزون. على invoice_basis لا قيد: إشعار الدائن يحمل المال. **لا إلغاء للمرتجع** (تصحيحه استلام جديد) | لا أخمّن إلغاء مخزنياً |
| إشعار الدائن | لبنود فاتورة مقيّدة، بسعر الفاتورة وضريبتها. المسموح: ما بقي دون خصم على بند الفاتورة، وما فُوتر وأُرجع ولم يُخصم، ولا يتجاوز إجماليه الرصيد المستحق. قيده مرآة قيد الفاتورة. يُلغى بقيد عكسي | لا خصم لبضاعة ما زالت عندك |
| الدفعة | تُوزَّع كاملة على فواتير مقيّدة لمورد **واحد**، كل تخصيص ضمن رصيد فاتورته. الرصيد = الإجمالي − المدفوع − المخصوم. لا دفعة مقدمة بلا تخصيص. قيدها مدين الموردين ودائن حساب أصول (صندوق/بنك). تُلغى بقيد عكسي فيعود الرصيد | لا قاعدة للدفعات المقدمة ولا للموافقة على الدفع |
| منع تكرار الدفع | مفتاح Idempotency، وفهرس فريد على (المؤسسة، المورد، مرجع الدفع) للدفعات غير الملغاة | المرجع يتحرر عند الإلغاء |
| إلغاء الفاتورة | مرفوض ما دام عليها دفعة أو إشعار دائن مقيّد (409) | يحفظ ترابط الأرصدة |
| المطابقة مع الدفتر | `GET /api/v1/procurement/reconciliation` يقارن رصيد المخزون وGRNI والموردين في الدفتر بما تقوله المستندات. **المخزون يُقارَن بقيمة الاستلام بسعر الأمر، لا بتقييم الصنف بتكلفته (`current_stock × unit_cost_minor`)** | فرق التقييم قرار محاسبي مفتوح |
| الصلاحيات في الواجهة | الصفحة تقرأ صلاحيات المستخدم من الخادم (`readSessionPermissions`) وتخفي ما لا يملكه. هذا إخفاء فقط: الخادم وقاعدة البيانات يفحصان كل طلب. ولا مسار API لقراءة الصلاحيات | يمنع كشف قائمة الصلاحيات لمن لا يحتاجها |
| غير مبني | استرداد فاتورة مدفوعة، دفعات مقدمة، موافقة على الدفع أو على فرق السعر، إلغاء المرتجع، تعدد العملات، FIFO/متوسط | كلٌّ يحتاج قراراً |
