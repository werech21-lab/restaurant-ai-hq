# تسليم تنفيذ Staging — Aether BI

التاريخ: 2026-10-28. الفرع: `cursor/erp-finance-inventory-crm`.

**لم يُنشأ مشروع مستضاف، ولم تُطبَّق ترحيلات على قاعدة خارج الجهاز، ولم يُلمس إنتاج، ولم يُدمج `main`.** اسم المشروع المستهدف **غير معروف**. لا مرجع مشروع، ولا منظمة، ولا منطقة.

## 1. حالة الجاهزية

| البند | الحالة |
| --- | --- |
| شجرة Git عند بداية الجلسة | نظيفة على الفرع، متقدمة على الأصل بالتزام `20e7556` غير المدفوع |
| TypeScript | خروج 0 |
| ESLint | خروج 0 |
| Vitest | 58 ملفًا، **1077** اختبارًا ناجحًا، 191.91 ثانية |
| البناء | خروج 0، تجميع 16.8 ثانية |
| Playwright وPostgres المحلي وRLS | **8** ناجحة، 5.4 دقيقة. الخادم لا يبدأ إذا فشل فحص العزل |
| ترحيلات `0001`–`0017` على قاعدة فارغة | نجحت محليًا على PGlite: صفر صفوف في الشركات والفواتير والأصناف والقيود وحركات المخزون، وافتراض `costing_method` هو `order_price`، وRLS مفعّل على الجداول الخمسة |
| مخطط الترحيل | تاريخ فارغ يضع الملفات السبعة عشر قيد الانتظار بالترتيب، وتاريخ حتى `0010` يُبقي `0011`–`0017` فقط ومن دون فجوات |
| حساب Supabase | غير مسجّل على هذا الجهاز |

سطر `relation "invoices" does not exist` وتحذيرات الموقع العابر وحد المعدل ظهرت داخل اختبارات الأمان الناجحة.

## 2. ما وُجد عن Supabase

- الأمر `supabase` غير موجود في المسار.
- `npx supabase` يشغّل الإصدار `2.122.0` دون تثبيته في المشروع.
- `SUPABASE_ACCESS_TOKEN` و`DATABASE_URL` غير موجودين في بيئة العملية. مجلد `.supabase` في ملف المستخدم فيه `telemetry.json` فقط، بلا رمز دخول.
- لذلك لا يمكن سرد المنظمات ولا معرفة إن كانت حصة الخطة المجانية تسمح بمشروع جديد.
- لم يُنفَّذ تسجيل دخول، ولا `projects create`، ولا ربط مشروع.

إنشاء مشروع مجاني ممكن كقدرة في منتج Supabase، وهو غير مثبت على هذا الحساب. التنفيذ يتوقف إلى أن يُسمّى الحساب والمشروع ويُؤكَّد أنهما مجانيان ومنفصلان عن الإنتاج.

## 3. المتغيرات المطلوبة

تُنسخ من `.env.staging.example` إلى `.env.staging`، والملف الحقيقي يتجاهله git. لا قيم هنا.

| المتغير | الدور |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | عنوان مشروع Staging فقط |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | مفتاح anon لذلك المشروع |
| `DATABASE_URL` | اتصال الخادم بمشروع Staging. لا يصل إلى المتصفح |
| `DATABASE_SSL` | `require` على المستضاف |
| `DATABASE_SSL_CA` | اختياري |

لا يُضبط `AETHER_E2E`. لا يوجد مفتاح service-role في التطبيق ولا في المثال. لا تُوضع قيم Staging في `.env.local`، لأن `npm run db:migrate` يقرأ ذلك الملف.

## 4. الترحيلات والنسخ والتراجع

الترتيب إجباري: `0001_core` ثم CRM والمخزون والمالية والإقلاع، ثم عمليات المخزون، ثم عروض البيع، ثم الذكاء، ثم المنتجات، ثم IAM، ثم المنظمة، ثم الدفتر، ثم المشتريات، ثم الشراء حتى الدفع، ثم إكمال GRNI والمدفوعات، ثم تجميد ملاحظات الفاتورة، ثم `0017` للتقييم التجريبي. كل ملف يملك شاهدًا في `scripts/migrate-lib.mjs`. `0017` يعتمد على إعدادات `0015` والدفتر في `0012`، ويبقي الافتراض المخزّن `order_price`.

المُرحِّل يرفض قاعدة فيها جداول وبلا سجل ترحيل، ويرفض فجوة أو مجموعًا اختباريًا مختلفًا. كل ملف داخل معاملة: الفشل يعمل `rollback` ولا يكتب `schema_migrations`.

النسخة الاحتياطية لا تُؤخذ الآن لأن المشروع غير موجود. بعد إنشائه وقبل أي ترحيل: نسخة من لوحة المشروع الجديد، أو تفريغ منطقي له فقط. التراجع عن تطبيق فاشل هو إعادة تشغيل المُرحِّل بعد إصلاح السبب. التراجع عن تطبيق ناجح هو استعادة تلك النسخة أو حذف مشروع Staging الفارغ. لا ترحيل عكسي، ولا استعادة فوق إنتاج.

الهوية تُراجع قبل التطبيق: مرجع المشروع في `DATABASE_URL` يطابق المرجع الذي وافق عليه المستخدم، وهو ليس مرجع الإنتاج. هذه الجلسة لم تشغّل `scripts/migrate.mjs` ولا `db:status:staging` ولا `staging-validate.mjs`.

## 5. القرارات المالية

قرار المستخدم في هذه الجلسة: السياسات غير المحسومة تبقى تجريبية. التفاصيل في القسم 6 من `docs/OPEN_ACCOUNTING_DECISIONS.md`. لم يتغير افتراض مخزّن ولم يُكتب شيء في `ERP_CORE_DESIGN.md`.

| القرار | إنتاج | تجربة |
| --- | --- | --- |
| تكلفة الصنف وتكلفة البضاعة | `order_price` | `moving_weighted_average` عند حفظ شركة اختبار مع حساب تكلفة البضاعة |
| أساس القيد | `invoice_basis` | `receipt_basis` لشركة التجربة إن أُريد تجنب فجوة التوقيت |
| فرق السعر والدفعات المقدمة وموافقة الدفعة | رفض الفرق فوق التسامح، ولا حساب عربون، ولا مسار موافقة جديد | لا يُبنى |
| استرداد فاتورة مدفوعة | لا حالة `refunded` | لا يُبنى |
| إلغاء مرتجع | التصحيح استلام جديد | لا إلغاء لمرتجع مرحّل |
| أوامر البيع والحجز | التحويل من عرض السعر إلى الفاتورة | لا كيان جديد |
| نقطة البيع | البيع فاتورة KWD | لا صندوق منفصل |
| العقود والرواتب | خارج النظام | لا قيد تلقائي |

## 6. ما يمكن تنفيذه تلقائيًا بعد الموافقة

بعد أن يُسمّى الحساب والمشروع المجاني ويُملأ `.env.staging` خارج git:

1. `npm run db:status:staging` للقراءة فقط، والتأكد أن `0001`–`0017` قيد الانتظار وأن لا جداول سابقة.
2. `node --env-file=.env.staging scripts/migrate.mjs` لتطبيقها بالترتيب.
3. إعادة `--status` والتأكد من `applied` ومن دون `CHANGED`.
4. إنشاء مستخدمين من لوحة Auth ثم `erp_bootstrap_tenant` لشركة اختبار واحدة، كما في دليل النشر.

لا تُنفَّذ هذه الخطوات في هذه الجلسة.

## 7. ما يحتاج موافقة

1. اسم المنظمة، واسم المشروع، والمنطقة، وتأكيد أن الخطة مجانية وأن المرجع ليس إنتاجًا.
2. إنشاء المشروع بعد ذلك التأكيد.
3. تطبيق `0001`–`0017` بعد النسخة الاحتياطية ومطابقة المرجع.
4. أي نقل لسياسة القسم 5 إلى الإنتاج.
5. دفع الفرع أو دمج `main`.
