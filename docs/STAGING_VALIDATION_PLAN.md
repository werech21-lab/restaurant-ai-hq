# خطة التحقق من قاعدة Supabase Staging (المرحلة 1.2)

**الحالة:** الأدوات مكتوبة ومختبرة محلياً على PGlite. **لم يُنفَّذ أي شيء على Staging** لأنه لا توجد بيانات اعتماد في بيئة العمل، والقيد الإلزامي يمنع الاتصال بأي قاعدة خارج التطوير دون موافقة.

## 1. الهدف

إثبات، على قاعدة Staging الحقيقية (Supabase) وبأدوار Supabase الفعلية (`anon` و`authenticated`)، أن:

1. كل مؤسسة ترى منتجاتها فقط، ولا ترى منتجات غيرها.
2. الصلاحية `inventory.item.read` شرط لقراءة المنتجات، والعضو بلا صلاحية لا يرى شيئاً.
3. لا يستطيع المتصفح الكتابة المباشرة في أي جدول يخص مؤسسة (إدراج أو تعديل أو حذف).
4. `token_hash` في `tenant_invitations` غير مقروء لأي مستخدم، والدعوات لا تُقرأ إلا بصلاحية `iam.member.read` داخل المؤسسة.
5. لا جدول يحمل `tenant_id` يسرّب صفوف مؤسسة لمؤسسة أخرى أو لمستخدم بلا مؤسسة.
6. `erp_bootstrap_tenant` لا يُستدعى من المتصفح.

## 2. الأدوات

| الأداة | الوظيفة |
| --- | --- |
| `scripts/staging-validate.mjs` | يشغّل الفحوص أعلاه داخل **معاملة واحدة تنتهي دائماً بـ ROLLBACK** |
| `scripts/ops-lib.mjs` | منطق الفحوص (`runIsolationChecks`) وحراس الأمان، ويعمل على أي عميل يملك `query()` |
| `scripts/products-report.mjs` | تقرير قراءة فقط عن منتجات بلا `tenant_id` (انظر `docs/PHASE_1_2_REPORT.md`) |
| `src/lib/__tests__/staging-validation-db.test.ts` | يثبت أن الفاحص ينجح على مخطط سليم **ويفشل** على مخطط معطوب (4 أنواع كسر) |

## 3. الحراس المبنية في الأداة

- `--expect-host <project-ref>` إلزامي (6 أحرف على الأقل). يُقارَن مع `user@host` في `DATABASE_URL`، وإن لم يتطابق تُرفض الأداة قبل أي اتصال. لا تُطبع كلمة المرور أبداً.
- `--i-understand-this-is-staging` إلزامي.
- لا تُطبّق الأداة أي ترحيل. تقارن ملفات `database/migrations` (بالـ checksum) مع `schema_migrations`، وتتوقف إن وُجد ترحيل معلّق أو معدَّل أو خارج الترتيب.
- كل البيانات مصطنعة: مستخدمون بعناوين `*.validation.invalid`، ومؤسستان بمعرّف `zz-validate-*`، ومنتجات `validate-*`.
- كل ما يُكتب يتم داخل `begin ... rollback`. الحالات المتوقع فشلها تعمل داخل `savepoint` كي لا تُفسد المعاملة. بعد الـ rollback تتحقق الأداة أن المؤسستين غير موجودتين.
- ملاحظة صريحة: التسلسلات (sequences) قد تتقدم رقماً حتى مع الـ rollback. هذا لا يغيّر أي بيانات.

## 4. خطوات التنفيذ (يقوم بها المسؤول بعد موافقته)

1. أنشئ ملف `.env.staging` (غير مودَع في git) فيه `DATABASE_URL` الخاص بـ **Staging** فقط، وليس الإنتاج.
2. اطبع حالة الترحيلات للقراءة فقط:
   `node --env-file=.env.staging scripts/migrate.mjs --status`
3. إن كانت 0009 و0010 معلّقتين: طبّقهما على **Staging فقط** بعد مراجعة بشرية (`scripts/migrate.mjs`). هذا خارج نطاق هذه الجلسة.
4. شغّل تقرير المنتجات (قراءة فقط):
   `node --env-file=.env.staging scripts/products-report.mjs --expect-host <ref>`
5. شغّل الفاحص:
   `node --env-file=.env.staging scripts/staging-validate.mjs --expect-host <ref> --i-understand-this-is-staging`
6. أرفق المخرجات (PASS/FAIL) بمحضر الإصدار. أي `FAIL` يمنع الانتقال للإنتاج.

## 5. ما يغطيه الاختبار المحلي وما لا يغطيه

| مغطى محلياً (PGlite) | غير مغطى إلا على Staging الحقيقي |
| --- | --- |
| منطق RLS والـ grants كما كتبتها الترحيلات | سلوك Supabase الفعلي لـ `auth.uid()` مع JWT حقيقي (يحاكيه الاختبار بنفس تعريف Supabase القائم على `request.jwt.claims`) |
| فشل الفاحص عند كسر سياسة أو منح صلاحية | أن يقبل `insert into auth.users (id, email)` على Staging دون أعمدة إلزامية إضافية (إن فشل، يُعدَّل الفاحص ولا تُمس القاعدة) |
| رفض `--expect-host` الخاطئ وعدم تسريب كلمة المرور | الصلاحيات الافتراضية الفعلية لمشروعك (default privileges) وأي جداول يدوية خارج `database/migrations` |
| رفض قاعدة غير مطابقة للترحيلات | سلوك pgbouncer/pooler مع `set local role` (استخدم الاتصال المباشر أو session pooler، لا transaction pooler إن فشل) |

## 6. ما لا تفعله الأداة عمداً

لا تغيّر مخطط، لا تحذف، لا تعيد تعيين القاعدة، لا تقرأ بيانات حقيقية (لا تستعلم إلا عن الكائنات المصطنعة والفهارس والصلاحيات)، ولا تتصل بالإنتاج.
